# 見積もりアプリ Version 1 要件定義

## 1. アプリの概要

### 何をするアプリか
丹内建機サービスの見積もり作成を支援するWebアプリ。作業人数・想定日数・1人1日単価・材料費・消耗品費・技術料・諸経費を入力すると、見積もり金額のたたき台を自動計算する。あわせて、その金額に決めた判断理由と、作業後の実績との差分を記録する。

### 何を目的にするか
- 父の見積もり作成時間を短縮する
- 経験・暗黙知に依存している単価・人数・日数の判断を、入力項目と記録として見える形にする
- 判断理由と実績差分を残し、次回以降の見積もり精度を上げる

見積もり判断そのものを自動化するのではなく、父が最終判断しやすい状態を作ることを目的とする。

### Version 1でやること
- 見積もりの新規作成・保存・一覧・詳細表示
- 作業条件に応じた推奨1人1日単価の表示と、単価候補からの選択・手動調整
- 工賃・材料費・消耗品費・技術料・諸経費の合計計算
- 見積もりに対するリスクアラート表示
- 判断理由メモの記録
- 作業後の実績入力と実績差分メモの記録

### Version 1でやらないこと
- Leafletによる安全マップ
- Blenderや3D配置
- 本格CAD
- AI自動見積もり
- 会計ソフト連携
- 在庫管理
- 外部公開用SaaS
- 見積書PDFの出力・印刷レイアウト
- 複数ユーザーでの共同編集・権限管理

## 2. 想定ユーザー

### メインユーザー
- 丹内建機サービスの代表（父）。見積もり金額を最終判断する本人
- 補助的に、入力を手伝う家族（開発者本人）

### 利用シーン
- 現場確認後や電話での依頼後に、事務所または自宅のPC・スマホで見積もり金額を出すとき
- 顧客に金額と納期を伝える前に、金額の根拠を確認するとき
- 作業完了後に、実際にかかった人数・日数・費用を記録するとき
- 似た案件の見積もりを作る前に、過去の見積もりと実績を見返すとき

### ユーザーが抱えている課題
- 1人1日単価をいくらにするかが毎回感覚頼りになる
- 何人で何日かかるかの見立てが人に伝えられる形で残っていない
- 手間代のみか、消耗品込みか、技術料込みかの区別が金額に反映されにくい
- 材料費にどの掛け率を使ったかが記録されない
- 顧客に提示する納期の根拠が残らない
- 見積もりと実績の差が振り返られず、同じ判断ミスを繰り返す

## 3. 必須機能

優先度は「高」「中」の2段階とする。Version 1ではすべて実装対象だが、画面の実装順は次を推奨する。

1. `/estimates/new`（新規作成）
2. `/estimates/[id]`（詳細）
3. `/estimates`（一覧）
4. `/estimates/[id]/edit`（編集）
5. `/estimates/[id]/result`（実績入力）

実績入力は実装順では最後だが、Version 1の完了条件に含める。実績入力がないと、父の見積もり判断が学習材料として残らないため、事業検証上は必須とする。

### 3-1. 見積もり新規作成（/estimates/new）
- 目的: 1件の見積もりを作成する入口。以下の各フォームをまとめる画面
- 入力項目: 案件名、顧客名、作業場所（任意）、見積もり日、顧客提示予定納期（任意）
- 表示・出力項目: 作業条件・工賃・材料費・その他費用・合計・アラート・判断理由メモの各セクション、保存ボタン
- 優先度: 高

### 3-2. 作業条件入力（WorkConditionForm）
- 目的: 単価と工数の判断材料となる条件を入力する
- 入力項目:
  - 作業人数（人）
  - 想定日数（日）
  - 作業負荷（低 / 中 / 高）
  - 消耗品を含むか（はい / いいえ）
  - 技術料を含むか（はい / いいえ）
  - 作業内容の簡単な説明（任意）
- 表示・出力項目: 延べ人日（作業人数 × 想定日数）
- 優先度: 高

### 3-3. 推奨1人1日単価の表示（LaborCostCalculator）
- 目的: 作業条件から推奨単価のたたき台を示し、判断の起点を作る
- 入力項目: 3-2の作業条件（自動連携）
- 表示・出力項目:
  - 推奨単価（円/人日）と、その根拠となるライン名
  - 判定ルール（Version 1では固定）:
    - 手間代のみ・負荷低〜中: 手間代最低ライン 30,000円
    - 通常案件: 会社維持ライン 50,000円
    - 負荷高、または消耗品込み、または技術料込み: 60,000〜72,000円の範囲を提示
- 優先度: 高

### 3-4. 単価候補からの選択
- 目的: 父が普段使っている単価の中から選べるようにし、入力を速くする
- 入力項目: 単価候補からの選択
  - 25,000 / 28,000 / 30,000 / 35,000 / 36,000 / 40,000 / 45,000 / 50,000 / 56,000 / 60,000 / 64,000 / 68,000 / 72,000 円
- 表示・出力項目: 選択中の単価。推奨単価と一致する候補は強調表示する
- 優先度: 高

### 3-5. 単価の手動調整
- 目的: 候補にない金額でも最終判断できるようにする
- 入力項目: 1人1日単価（自由入力、円）
- 表示・出力項目: 採用単価。推奨単価との差額
- 優先度: 高

### 3-6. 工賃計算（LaborCostCalculator）
- 目的: 採用単価と工数から工賃を自動計算する
- 入力項目: 作業人数、想定日数、採用単価（自動連携）
- 表示・出力項目: 工賃 = 作業人数 × 想定日数 × 採用単価
- 優先度: 高

### 3-7. 材料費計算（MaterialCostForm）
- 目的: 材料の仕入れ額と掛け率から材料費を出す
- 入力項目:
  - 材料明細（複数行）: 材料名、仕入れ単価、数量
  - 掛け率（例: 1.0 / 1.2 / 1.3 / 1.5、または自由入力）
- 表示・出力項目: 材料仕入れ合計、材料費（仕入れ合計 × 掛け率）
- 優先度: 高

### 3-8. 消耗品費・技術料・諸経費の入力
- 目的: 工賃・材料費以外の費用を漏れなく積み上げる
- 入力項目:
  - 消耗品費（円、任意）
  - 技術料（円、任意）
  - 諸経費（円、任意。交通費・運搬費などをまとめた額）
- 表示・出力項目: その他費用合計
- 優先度: 高

### 3-9. 見積もり合計の表示（EstimateSummary）
- 目的: 顧客提示額のたたき台を一目で確認する
- 入力項目: なし（各セクションから自動集計）
- 表示・出力項目:
  - 工賃、材料費、消耗品費、技術料、諸経費の内訳
  - 小計（税抜）
  - 消費税額（税率は10%固定）
  - 合計（税込）
  - 参考: 1人日あたり実質単価 = 小計 ÷ 延べ人日
- 優先度: 高

### 3-10. リスクアラート（EstimateRiskAlert）
- 目的: 安すぎる・条件漏れの見積もりに気づけるようにする
- 入力項目: なし（入力内容から自動判定）
- 表示・出力項目: 以下に該当する場合、警告文を表示する
  - 採用単価が30,000円未満（手間代最低ライン割れ）
  - 採用単価が50,000円未満（会社維持ライン未満）
  - 消耗品込みなのに消耗品費が0円
  - 技術料込みなのに技術料が0円
  - 材料明細があるのに掛け率が1.0以下
  - 作業人数または想定日数が0
- 優先度: 高

### 3-11. 判断理由メモ（EstimateReasonMemo）
- 目的: なぜその単価・人数・日数にしたかを言葉で残す
- 入力項目:
  - 単価を決めた理由（テキスト）
  - 人数・日数を決めた理由（テキスト）
  - 納期を決めた理由（テキスト、任意）
- 表示・出力項目: 入力したメモ。詳細画面でそのまま表示
- 優先度: 高

### 3-12. 見積もり保存
- 目的: 作成した見積もりをあとから参照・検証できるように保存する
- 入力項目: 3-1〜3-11の内容
- 表示・出力項目: 保存完了メッセージ、詳細画面への遷移。ステータス（下書き / 提示済み / 受注 / 失注 / 完了）
- 優先度: 高

### 3-13. 見積もり一覧（/estimates）
- 目的: 過去の見積もりを一覧で確認し、詳細へ移動する
- 入力項目: なし
- 表示・出力項目: 見積もり日、案件名、顧客名、合計（税込）、ステータス、実績入力済みかどうか。新しい順に表示。新規作成ボタン
- 優先度: 中

### 3-14. 見積もり詳細（/estimates/[id]）
- 目的: 1件の見積もり内容と判断理由をまとめて確認する
- 入力項目: なし
- 表示・出力項目: 案件情報、作業条件、採用単価と推奨単価、内訳と合計、アラート、判断理由メモ、実績（入力済みの場合）。編集・実績入力への導線
- 優先度: 高（実装順2。保存後の着地画面）

### 3-15. 見積もり編集（/estimates/[id]/edit）
- 目的: 提示前の見積もりを修正する
- 入力項目: 3-1〜3-11と同じ
- 表示・出力項目: 新規作成と同じ画面構成。既存値が初期表示される
- 優先度: 中

### 3-16. 実績入力（/estimates/[id]/result、EstimateResultForm）
- 目的: 実際にかかった人数・日数・費用を記録し、見積もりと比較する
- 入力項目:
  - 実際の作業人数、実際の作業日数
  - 実際の材料仕入れ合計
  - 実際の消耗品費、技術料、諸経費
  - 実際の受注金額（税抜）
  - 作業完了日
- 表示・出力項目: 見積もりと実績の差（人日、材料費、その他費用、金額、実質単価）
- 優先度: 高（実装順5。Version 1完了必須。事業検証上、見積もり判断を学習材料として残すために必要）

### 3-17. 実績差分メモ
- 目的: 差が出た理由を言葉で残し、次回に活かす
- 入力項目: 差分の理由（テキスト）、次回に向けた気づき（テキスト、任意）
- 表示・出力項目: 詳細画面で見積もり時の判断理由メモと並べて表示
- 優先度: 高（実績入力とセット。Version 1完了必須）

## 4. 余裕があれば追加する機能

Version 1では必須にしない。/estimates 系が安定して動いたあとに検討する。

- ダッシュボード（/dashboard）: 最近の見積もり数件と、実績未入力の件数を表示するだけの最小画面
- 設定画面（/settings）: 単価候補、掛け率の初期値、消費税率の変更
- 過去見積もり検索: 顧客名・案件名での絞り込み
- 作業パターン登録: よくある作業の人数・日数・単価をテンプレートとして保存し、新規作成時に呼び出す
- CSV出力: 見積もり一覧と実績を表計算ソフトで検証するための出力
- 安全マップ連携のための作業条件タグ: 高所・重機使用・公道近接などのタグ付け。将来の安全マップ機能に渡すための下準備のみ

### Version 1では作らないもの
- Leafletによる安全マップ
- Blenderや3D配置
- 本格CAD
- AI自動見積もり
- 会計ソフト連携
- 在庫管理
- 外部公開用SaaS

## 5. 非機能要件

### 技術方針
- JavaScriptで実装する
- TypeScriptは使わない
- Next.js App Routerを使う。ページは page.js ベースで進める
- スタイルは通常のCSS / CSS Modulesを使う。Tailwind CSSは使わない
- Supabaseを使う前提で設計する。ただし、DB実装・接続コードは要件定義後の別ステップで行う

### セキュリティ・データ管理
- SupabaseのRLS（Row Level Security）を有効にする前提で設計する。テーブルにはユーザーIDを持たせ、本人のデータのみ読み書きできる方針とする
- Supabase URLやAnon Keyは .env.local に置き、Git管理しない
- .env* は .gitignore に含める
- 見積もりデータ・実績データは、あとから検証に使える形で保存する
  - 合計だけでなく、作業人数・日数・単価・掛け率などの入力値をそのまま残す
  - 推奨単価と採用単価を両方保存し、どれだけ調整したかを追えるようにする
  - 見積もりと実績は別テーブルとし、見積もりIDで紐づける
  - 作成日時・更新日時を持たせる

### 画像アップロード（将来追加時の制限）
Version 1では画像アップロードは実装しない。将来、安全マップや見積書画像のアップロードを追加する場合は以下を守る。
- 画像は1枚あたり5MB以下を目安にする
- 対応形式は jpg / png / webp を想定する
- 大量アップロードはVersion 1では扱わない

### 開発のしやすさ
- 初学者が扱えるよう、画面と機能を小さく分ける。1つのコンポーネントは1つの役割に絞る
- 最初から複雑なディレクトリ構成にしない。app/ 配下に画面、components/ にコンポーネント、lib/ に計算ロジック程度に留める
- 計算ロジック（工賃・材料費・合計・推奨単価・アラート判定）は画面から切り離し、単独で動作確認できるようにする

### 利用環境
- PCのブラウザを主とし、スマホでも入力できる程度のレイアウトにする
- 利用者は1〜2名。同時編集は考慮しない

## 6. 実装時に注意すべきこと

- 最初から作り込みすぎない。動く最小の画面を先に作り、あとから項目を足す
- /estimates/new を最優先にする。一覧・詳細・実績はそのあと
- 父が実案件1件を作れることを最優先にする。見た目より入力のしやすさと計算の正しさを優先する
- 推奨単価は正解ではなく、たたき台として扱う。画面上でも「推奨」「参考」と表現し、断定しない
- 最後に必ず手動調整できるようにする。推奨単価や候補にない値でも保存できること
- 判断理由メモを必ず残せるようにする。空欄でも保存はできるが、未入力時は注意表示を出す
- 実績入力を入れて、次回の見積もり改善につなげる。見積もりと実績を並べて見られる画面を用意する
- 単価候補・掛け率・消費税率などの数値は定数として1か所にまとめ、変更しやすくする
- Leaflet、安全マップ、3D配置は将来拡張として分離する。Version 1のデータ構造やコンポーネントに混ぜない
- Supabase連携は、要件定義後に別ステップで実装する。まずはフォームと計算が画面上で動く状態を作り、その後に保存・読込を接続する
- .env.local、utils/supabase/ の作成はSupabase連携のステップで行う
